# Koudelka (USA) decompilation

PlayStation 1, Sacnoth / SNK / Infogrames, 1999–2000. Four discs.

The repository holds no game bytes. Disc images live in `Koudelka_Game_Data/`; everything extracted from them
goes to `extracted/`. Git ignores both.

## Extracting

```powershell
py -3.14 tools/extract_iso.py "Koudelka_Game_Data/Koudelka (USA) (Disc 1).bin" extracted/disc1 > extracted/disc1.files.txt
```

Form 1 files come out as plain 2048-byte sectors. XA/STR files (Form 2 audio, interleaved movie data) come out as
raw 2336-byte sectors (subheader + data), so no audio or video data is lost.

## Building

The goal is a **functionally identical** build: one that behaves like retail, not one that matches it byte for
byte. The build splits each target with splat, compiles the game code from `src/` with the original compiler
(PsyQ 4.4), assembles the rest, relinks with GNU binutils and extracts a flat binary. Today all seven targets also
come out byte-identical.

Two modes (`configure.py --mode`):

- `functional` (default). Code may move. Overlays take the EXE's symbols, and EFFECT takes BATTLE's, from the linked
  ELFs (`tools/extern_syms.py`), so they follow the code when it shifts. The gate is `tools/functional_check.py`:
  - **fit**: the EXE's BSS ends at or before the overlay slot `0x800B6DF0`, and no overlay is larger than retail
  - **pins**: the 114 overlay entry points that another image reaches by absolute address (`config/pins.txt`,
    generated by `tools/gen_pins.py`) stay where they are
  - SHA-1 is printed per image as `identical` / `differs`, for information only

  Green is `functional check: OK`.
- `matching`. Every image must equal retail (`tools/check.py`). Green is one `check: OK <sha1>` per target.

The EXE also calls 28 addresses in the overlay slot where no overlay function starts (mid-function in FIELD, or past
an overlay's end). These are most likely code or data loaded from other files. They stay absolute and are listed as
comments in `config/pins.txt`.

```powershell
py -3.14 -m venv .venv
.venv/Scripts/python.exe -m pip install "splat64[mips]==0.50.1" ninja ninja_syntax
.venv/Scripts/python.exe configure.py
```

`configure.py --no-split` skips re-splitting; after that, `.venv/Scripts/ninja.exe` builds incrementally (about 3 s
after an edit to a source file). Re-split after you decompile a function, so its `.s` moves from `nonmatchings/` to
`matchings/`.

### Sources

Game code is C++ (vtables, `__builtin_new`), so every target's code is a `.cpp` file:

| Target | Source | Kept as assembly |
|---|---|---|
| `SLUS_010.51` | 35 units in `src/main/`, one per original source file: cut after each `.ctors` entry and wherever the jump tables' address mod 8 changes (`tools/jtbl_classes.py`). `main_a.cpp`, `main_b.cpp`, `u_<start>.cpp`, and `sound.cpp` (the sound driver, `0x8008B6B0`–`0x80094910`, PsyQ 4.1). Only units with jump tables have a rodata segment, starting at their first table | `.ctors`/`.dtors` tables, PsyQ library code and rodata, `.data`/`.sdata` |
| each overlay | `src/<overlay>/<overlay>.cpp`: all of its code and leading rodata | trailing `.data` |

splat writes these files once, with one `INCLUDE_ASM` / `INCLUDE_RODATA` line per function and rodata symbol, in
address order. It never overwrites them; delete one to regenerate it. Functions and rodata used by only one function
(jump tables, strings) live in `asm/<target>/nonmatchings/<file>/`.

`tools/cc.py` compiles each source:
1. `CPPPSX.EXE`, with the defines `CCPSX.EXE` passes
2. `CC1PLPSX.EXE` (or `CC1PSX.EXE` for `.c`)
3. `tools/maspsx_extern.py`
4. GNU `as`

It also writes a depfile. Flags come from `config/toolchain.toml`: `-O2 -G8`, with per-file overrides under
`[compiler.overrides]`.

Two things are specific to this compiler:
- **`INCLUDE_ASM` order.** With `-G8`, `CC1PLPSX` outputs every function after all top-level `asm` statements.
  `include/common.h` therefore wraps each include in a dummy `__maspsx_include_asm_hack_*` function, which maspsx
  strips. Without it, decompiled functions drift away from their neighbours.
- **Small globals use `$gp` only in their defining file.** ASPSX reached a small global through `$gp` in the
  source file that defines it, and with `lui` everywhere else (main_b's round-2 scan: for each of 30 symbols
  reached both ways, the `$gp` uses form one contiguous range). Our units declare those globals `extern`, so
  `tools/cc.py` collects the symbols a unit's own retail asm reaches through `%gp_rel` and
  `tools/maspsx_extern.py` gives only those `$gp`. A small extern not on that list gets the assembler's `lui`
  macro form.

### Decompiling a function

1. Check it on its own:

   ```powershell
   .venv/Scripts/python.exe tools/try_compile.py my.cpp func_XXXXXXXX --unit src/main/main_a.cpp
   ```

   This diffs it against retail, compiled with the build's own flags for that source file (`--unit`). Reference
   asm comes from `nonmatchings/` or `matchings/`.
2. Replace the function's `INCLUDE_ASM(...)` line in the `.cpp` with the code.
   - Wrap free functions, and the asm functions they call, in `EXTERN_C` (`include/common.h`), so names stay
     `func_XXXXXXXX`.
   - Member functions get mangled names; add those to `config/symbols/` instead.
   - Declare globals as `EXTERN_C` with their retail names rather than defining new ones. Defining a variable adds
     storage, and the EXE must not grow.
3. Re-split and build: `configure.py` (functional) or `configure.py --mode matching`.

In functional mode the EXE must still fit: its BSS has to end by `0x800B6DF0`, where the overlays load. Retail ends
exactly there, so the EXE has **no room to grow**. A decompiled function may be the same size or smaller.

## Targets

| File | Size | Load address | Notes |
|---|---|---|---|
| `SLUS_010.51` | 0xA5000 text | `0x80010000`–`0x800B5000` | entry `0x800A0A20`, sp `0x801FFFF0`; `.rodata` from `0x80010000`, `.text` `0x800186B0`, `.data` `0x800A4514`, `.sdata` at `$gp` = `0x800B4BFC`, BSS `0x800B4EE8`–`0x800B6DF0` |
| `BIN/FIELD.BIN` | 0x33AB0 | `0x800B6DF0` | overlay id 4 |
| `BIN/BATTLE.BIN` | 0x1EFBC | `0x800B6DF0` | overlay id 5 |
| `BIN/MOVIE.BIN` | 0x15CB8 | `0x800B6DF0` | overlay id 6 |
| `BIN/CAPTURE.BIN` | 0xC42C | `0x800B6DF0` | overlay id 7 |
| `BIN/GAMEEND.BIN` | 0xCB0 | `0x800B6DF0` | overlay id 8 |
| `BIN/EFFECT.BIN` | 0xFAA0 | `0x800D5DAC` | overlay id 9; loads directly after BATTLE |

Each overlay is laid out as `.rodata` (id word, entry table, jump tables, strings), then `.text` (starting at the
first prologue), then a little `.data`; the exact offsets are in `config/<overlay>.yaml`.

The first word of each overlay is its id; a short table of entry pointers follows it. Load addresses were found by
aligning `jal` targets with `addiu sp,sp,-N` prologues; every overlay agrees, with no ambiguity.

The EXE and all six overlays are byte-identical on all four discs. The SLUS names differ per disc
(`SLUS_010.51`, `011.00`, `011.01`, `011.02`), and so do `SYSTEM.CNF`, `BIN/DISKNO<n>.BIN` (disc id data, not code)
and the `MOVIE/` contents. Disc 1 is the reference.

## Toolchain evidence

- SDK: **PsyQ 4.6**. `tools/psyq_version.py` matches 155 library objects for 4.6 against 143 for 4.7 and ≤118 for
  4.5 and earlier (LIBGPU `sys.c` 1.140, 1998-01-12).
- Language: **C++** for at least part of the game code. The EXE contains the GCC 2.x C++ runtime (`__builtin_new`,
  `__builtin_delete`, `__do_global_dtors`), and `func_800186E8` makes a GCC 2.x virtual call (vtable entries of
  `{short delta; short index; pfn}`) through a null-checked virtual-base pointer.
- Compiler: **GCC 2.8.x, from PsyQ 4.3 or 4.4.** That is older than the 4.6 libraries. The pick is PsyQ 4.4
  (CC1PSX/CC1PLPSX 2.8.1), with maspsx emulating ASPSX 2.81 and the ASPSX divide-by-zero checks; all of this is in
  `config/toolchain.toml`. `tools/try_compile.py` runs
  CC1PSX/CC1PLPSX → maspsx → GNU as and diffs one function against retail, with relocations masked. The matching
  sources are in `tests/compiler/`:
  - `func_800186E8` (C++ loop) and `func_8006F630` (switch with jump table) match exactly on 4.3 and 4.4 only.
  - 4.0/4.1 (GCC 2.7.2) differ in the epilogue.
  - 4.5 (egcs) and 4.6 (2.95) move the loop test to the bottom and lay out the switch differently.
  - 2.8.0 and 2.8.1 gave identical output in every test.
  - ASPSX 2.67–2.86 all give the same result on these functions. Later evidence picks **2.81** (PsyQ 4.5's):
    `func_80065870` needs its `$gp`-relative `la`, and nothing already matched regresses.
  - Divides: every `div` in the game code (EXE and overlays) carries ASPSX's zero checks (`break 7`/`break 6`);
    `func_80089A4C` matches only with them.
  - **The sound driver is different:** `0x8008B6B0`–`0x80094910` was built with GCC 2.7.2 (PsyQ 4.1, ASPSX
    2.67), no `$gp` and no divide checks. Compiling `main_b` with 4.1 breaks every 4.4 function up to
    `func_8008B630` and none after; about 25 functions there match only with 4.1.
  - PsyQ 3.6 is a 16-bit DOS build and can't run on 64-bit Windows.
  - The 2.7.2 builds need `TMPDIR` set to a Windows path (the tool does this).

  | PsyQ | CC1PSX | ASPSX |
  |---|---|---|
  | 3.6 | 2.7.2.SN.1 | 2.34 |
  | 4.0 | 2.7.2 SN32.3.7.0002 | 2.56 |
  | 4.1 | cygnus-2.7.2-970404 | 2.67 |
  | 4.3 | 2.8.0 SN32 Build 4.0.0007 | 2.77 |
  | 4.4 | 2.8.1 SN32 BUILD 4.0.0010 | 2.79 |
  | 4.5 | egcs 2.91.66 (1.1.2) | 2.81 |
  | 4.6 | 2.95.2 BUILD 4.0.0030 | 2.86 |

  `CC1PSX`/`CC1PLPSX` don't preprocess, so test files can't use `#define` yet (`CPPPSX.EXE` would add that).
- Other strings: `Copyright 1996-1999 Programmed by Hidenori Suzuki` at `0x800B18C6`.

## C++ translation units

`.ctors` (`0x80010000`, 27 entries) and `.dtors` (`0x8001006C`, 22 entries) list each source file's
`_GLOBAL_$I$`/`$D$` function. GCC emits that function at the end of the file, so these entries mark real file
boundaries in the EXE. `main_a.cpp`/`main_b.cpp` are split at one of them (`func_80054A04`); the rest are where
further splits go. `func_8001C2AC` (a
constructor right after a tail call) is declared in `config/symbols/main.txt`, so the table holds a symbol rather
than a raw address.

## Data files of note

- `BIN/SECT.DAT`: 512 × (sector, byte size) table, 97 entries used. Entry 1 points at `MONSTER/BIM.AR`, so this is
  probably a lookup table into the big archives.
- `_ZYXWVUT.ZYX` (root): padding file. All zeros on disc 1.

## Ghidra

Project: `C:\Users\jamie\Documents\Shadow Hearts 2 Decomp\ghidra Project\Koudelka.gpr` (Ghidra 12.1.4 with
ghidra_psx_ldr and GhydraMCP). `tools/ghidra_scripts/KoudelkaOverlays.java` is the import pre-script: it adds the
six overlays as overlay blocks, seeds functions at `jal` targets and sets the PsyQ version to 4.6.
`ExportFunctions.java` dumps the function list to CSV.

After import, two analysis passes and seeding:

| Block | Functions | Named by PsyQ signatures | Bytes |
|---|---|---|---|
| main `.text` | 2,072 | 526 | 365,168 |
| FIELD | 362 | 0 | 110,124 |
| BATTLE | 254 | 0 | 72,752 |
| EFFECT | 152 | 0 | 32,616 |
| MOVIE | 150 | 28 (libpress / MDEC) | 40,356 |
| CAPTURE | 125 | 0 | 28,108 |
| GAMEEND | 0 | — | — |

Then two scripts bring it in line with splat. Both are idempotent; rerun them after a re-split, then save.
1. **`KoudelkaSeedFunctions.java`, with the list from `tools/ghidra_function_list.py`.** It creates every function
   splat knows (5,493; Ghidra's analysis had found 3,375), GAMEEND's included. It also gives the default-named ones
   our `func_XXXXXXXX` names.
2. **`KoudelkaFixRefs.java`, with the list from `tools/ghidra_pointer_list.py`.** It fixes references that cross
   address spaces: five overlays share `0x800B6DF0`, and EFFECT loads after BATTLE, so Ghidra had sent any
   address in that range to its empty default `RAM` block. It does three things:
   - **Retargets references.** BATTLE references above `0x800D5DAC` now go to EFFECT, EFFECT references below it
     go to BATTLE, and EXE references go to the one overlay with a label at that address. The first run moved 218.
   - **Marks pointers.** It marks the 10,495 pointer words splat knows (vtables, jump tables, script tables) as
     pointers into the right space; 3,335 were new.
   - **Removes artifacts.** It deletes the one-byte "functions" those references had created in `RAM` (102).

Left after that: 23 EXE calls into the overlay range.
- Six target an address where two overlays both have a function (for example `0x800BCCC0`, in FIELD and CAPTURE);
  the EXE calls whichever is loaded.
- The rest go to addresses no overlay has a function at, which probably means Ghidra disassembled data in `.text`.

GhydraMCP runs scripts only when Ghidra is started with `GHYDRA_ALLOW_SCRIPTS=1`, and the folder
`%USERPROFILE%\ghidra_scripts` has to exist before Ghidra starts.
